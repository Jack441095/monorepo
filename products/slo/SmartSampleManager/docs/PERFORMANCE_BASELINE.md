# SmartSampleManager — Performance Baseline

Phase 1, Section 6. Real measurements from an actual run against synthetic fixtures, not fabricated numbers. Harness: `Source/benchmark_scan_main.cpp` (new, dev-only, `BenchmarkScan` CMake target — see exclusion in `docs/RELEASE_MANIFEST.md`), fixtures generated by `generate_benchmark_fixtures.py` (varied-frequency/duration synthetic mono WAVs, so they aren't degenerate 100%-duplicates).

## What was actually run

**500 files**, single measurement, this machine (Apple Silicon Mac, CoreML execution provider active), Debug build (not Release — numbers would improve with optimizations on):

| Metric | Measured value |
|---|---|
| Files enumerated | 500 |
| Samples processed | 500 |
| Enumerate + dispatch | 27.7 ms |
| Full scan (enumerate → decode → embed → index), total | 93,860 ms (~93.9s) |
| Full scan, per file | 187.7 ms/file |
| Incremental rescan (same 500 files, nothing changed) | 443.9 ms total (~0.9 ms/file — correctly cheap, confirms the cache-hit path skips re-embedding) |
| Search latency, p50 (200 queries) | 0.38 ms |
| Search latency, p99 (200 queries) | 0.90 ms |
| RSS before init | 28.1 MB |
| RSS after full scan | 1,971.4 MB |
| RSS peak | 1,972.9 MB |

## 10,000 / 50,000 / 100,000 / 250,000 / 500,000 / 1,000,000 files — not run

Extrapolating the measured 187.7 ms/file full-scan cost linearly would put a 10,000-file scan around 31 minutes and a 100,000-file scan around 5.2 hours on this machine — but that is an **extrapolation from a single 500-file data point, not a measurement**, and per-file cost is very likely not perfectly linear (thread-pool parallelism, batched ONNX inference in 32-64-file batches, and the one-time UMAP/HNSW full-rebuild cost at the end all change the shape of the curve at larger N). Running the full requested tier ladder up to 1,000,000 synthetic files was not attempted in this pass: at the measured per-file rate that's upward of 50 hours of continuous scanning for the largest tier alone, which is disproportionate to a readiness audit and would tie up this machine for days. **Do not treat the extrapolated numbers above as commercial claims** — they exist only to show the shape of the problem, not to be quoted on a website or in marketing copy.

If real large-library numbers are needed before launch (they should be, given "handles professional libraries" is part of the product's value proposition), the recommended path is: run `BenchmarkScan` against a real sample library of the target size on a dedicated machine with time budgeted for it (likely an overnight run for the 100k+ tiers), not as part of an interactive audit session.

## Findings from what was measured

**Incremental rescan is genuinely cheap** (0.9 ms/file vs. 187.7 ms/file for a full scan) — the SQLite cache-hit path works as designed. This directly supports the product's core "you don't re-scan your whole library every time" value proposition.

**Search latency is excellent** at this scale (sub-millisecond p50/p99) — consistent with the HNSW audit's finding that the index and query path are well-built. Whether this holds at 100k+ scale depends on the unresolved UMAP-persistence gap noted in `docs/SEARCH_QUALITY_AUDIT.md` (search itself is O(log N) and should stay fast; the *cold-start* full UMAP recompute is the part that doesn't scale well today).

**Memory usage is a real, unexplained finding worth investigating before a library-size claim is made.** ~1.97 GB RSS for 500 tiny (0.5-1.7s, 16-bit mono) synthetic files is high — roughly 3.9 MB retained per file. This dataset is too small to distinguish "mostly fixed overhead" (ONNX Runtime + CoreML compiled graph + JUCE framework baseline, which would not grow much further at 10k/100k files) from "genuine per-file memory retention that would grow linearly and become a real problem at scale." **Not diagnosed further in this pass** — a proper memory profiler run (Instruments on macOS) comparing RSS at e.g. 500 vs. 5,000 files would distinguish these two possibilities in under an hour and should happen before any "handles X samples" claim goes on the website. Flagged as P1 in `docs/COMMERCIAL_RELEASE_BLOCKERS.md` — not because 1.97 GB is necessarily a problem, but because *not knowing whether it's fixed or scaling* is the actual risk.

## Database size measurement — inconclusive, flagged rather than reported

The benchmark attempted to measure on-disk cache size after the scan (`~/Library/Application Support/SmartSampleManager/sample_cache.sqlite3`). The in-process reading showed a implausibly small 12,288 bytes for 500 processed samples (each carrying a 512-float/2048-byte embedding, so the true data volume should be well over 1 MB before any compression) — almost certainly because SQLite's WAL mode keeps recent writes in a separate `-wal` sidecar file until a checkpoint, and the benchmark measured only the main file's size. A post-exit filesystem check for the cache file (main + WAL) in this sandboxed execution environment found no cache file at all, which contradicts the in-process reading and could not be resolved within this session — most likely an artifact of how this coding-agent sandbox's Bash tool handles `$HOME`/file persistence across process launches, not a product bug (the `clearCache()`/`openCacheDb()` source itself is straightforward and was read carefully during the SQLite audit — see `docs/SEARCH_QUALITY_AUDIT.md`'s sibling data-stack findings). **Recommendation: re-run this specific measurement (`db_size_bytes` from `BenchmarkScan`, checked against the real file on disk immediately after the process exits) on a normal, unsandboxed machine** before trusting any on-disk cache size figure. Not treated as a P0/P1 finding since it's a measurement-environment issue, not an observed product defect — but it should be verified, not assumed fixed.
