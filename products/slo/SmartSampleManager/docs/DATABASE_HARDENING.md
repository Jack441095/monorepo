# SmartSampleManager — SQLite Cache Hardening

Phase 2, Sections 29-31. Addresses `docs/COMMERCIAL_RELEASE_BLOCKERS.md` P1 #12 (no automated
corruption detection) and P1 #13 (no `busy_timeout` for concurrent multi-instance writes).

## Changes made (`Source/SampleManagerEngine.cpp`, `openCacheDb()`)

1. **`PRAGMA busy_timeout=5000`** — added immediately after the existing `journal_mode=WAL`/
   `synchronous=NORMAL` pragmas. Previously, two plugin instances scanning simultaneously could
   hit an immediate `SQLITE_BUSY` on whichever instance lost a write race (per
   `docs/REALTIME_SAFETY_AUDIT.md`'s finding). Now a write blocks up to 5s waiting for the other
   connection's transaction to finish before failing — long enough to cover a normal
   upsert-batch write under real contention, short enough not to hang indefinitely if something
   is actually wedged.

2. **Integrity check on every open (`PRAGMA quick_check`)** — a new `quickCheckPassed()` helper
   runs once per `openCacheDb()` call (not on the recursive re-open after quarantine, to prevent
   an infinite loop). `quick_check` is SQLite's cheaper alternative to `integrity_check` — it
   verifies page/index structure without walking every row, so it doesn't meaningfully add to
   startup latency.

3. **Quarantine-and-rebuild on corruption** — if `quick_check` fails, the main DB file plus its
   `-wal`/`-shm` sidecars are renamed with a `.corrupt-<timestamp>` suffix (not deleted — kept on
   disk in case forensic inspection is ever needed) and a fresh cache DB is opened in its place.
   **Only the derived cache is ever touched** — this is metadata/embeddings that get
   regenerated by rescanning, never the user's original sample audio files. A quarantine event is
   logged via `AppLogger` with an explicit "source audio files are not affected" message, so a
   user seeing the log doesn't panic about their library.

4. **`checkCacheIntegrity()`** — a new public method exposing the same `quick_check` for testing/
   diagnostics (returns false if the cache isn't open).

## What was NOT changed

- **Multi-instance concurrent read/write correctness** — WAL mode already permits concurrent
  readers with one writer; this pass only bounds the wait when a writer collision happens, it
  doesn't change the underlying concurrency model. `docs/REALTIME_SAFETY_AUDIT.md`'s assessment
  that this is architecturally sound stands.
- **Schema versioning beyond the existing additive-`ALTER TABLE`-per-migration pattern** already
  in `openCacheDb()` — that pattern (try to add a column, ignore the "duplicate column" error if
  it already exists) is simple and has worked across several prior schema additions; no evidence
  it needs replacing with an explicit `schema_version` table this pass.
- **A production migration framework** — not warranted at this scale (single local SQLite file,
  handful of columns); would be over-engineering per the master prompt's own guidance.
