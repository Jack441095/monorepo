## Key Question 1 — Small-model landscape refresh (2B–14B class, 16 GB alongside Ableton)

### Takeaway
The 2–5B chat-model front runners for a 16 GB M3 are now **Qwen3.5-4B** (Apache-2.0, Feb 2026, vision-capable, strong tool-call scores for its size) and **Gemma 4 E4B-it** (Apache-2.0, Mar 2026, native function calling, audio input). Both are same-or-better than the KENN baseline Qwen3-4B-2507 on published benchmarks; neither is a drop-in — both need a runtime newer than KENN's pinned Ollama 0.34.4 and both bring a vision encoder that costs memory. No 2026 refresh of Llama (none since Llama 4, Apr 2025), Phi, SmolLM, or Ministral (Ministral 3 = Nov 2025) changes this picture.

## Key Question 2 — Structured / constrained output status (Ollama, llama.cpp GBNF, MLX)

### Takeaway
Typed tool-call planning has first-class local support on every runtime KENN might use: Ollama `format` (JSON schema) plus `response_format` on the OpenAI-compatible endpoint, llama.cpp `--json-schema`/`response_format` plus raw GBNF grammars, and MLX via Outlines' `MLXLM` adapter (mlx-lm itself has no grammar layer). Reliability guidance is consistent across vendors — schema in the prompt as well, temperature 0 — and Ollama fixed single-pass schema handling on thinking models in 0.34.4, while the MLX runner gained structured-output support in v0.33.1 (2026-08-26). No source publishes measured schema-adherence rates for small models, which is a KENN measurement gap, not a tooling gap.

### Cited Findings
- **Ollama structured outputs** work via a `format` field that accepts `"json"` or a JSON schema, or `response_format` on `/v1/chat/completions`. Documented tips: keep schemas in Pydantic/Zod for validation, lower temperature (0) for determinism, and pass the schema in the prompt as extra grounding. Ollama's own note: cloud models do not support structured outputs — this is a local-only feature today. [Ollama docs: Structured Outputs](https://docs.ollama.com/capabilities/structured-outputs) (fetched 2026-10-15 via docs.ollama.com llms-full.txt)
- **Ollama thinking + schema**: v0.34.4 (2026-09-23) changed structured outputs on thinking models to "apply in a single pass, making them faster and more reliable". Ollama updated "llama.cpp, MLX, and XGrammar" in the same release, i.e. schema enforcement is XGrammar-based locally. [Ollama v0.34.4 release notes](https://github.com/ollama/ollama/releases/tag/v0.34.4)
- **Ollama MLX runner + schemas**: v0.33.1 (2026-08-26) shipped `mlxrunner: add structured output support` — schema enforcement exists on both Ollama runners, though whether they behave identically is untested. [V] [Ollama v0.33.1 release notes](https://github.com/ollama/ollama/releases/tag/v0.33.1)
- **Ollama tool calling** is a documented capability with single-shot, parallel, multi-turn and streaming tool calling; the docs' examples use `qwen3` and pass JS/Python function schemas; `tool_choice` is *not* supported on the Anthropic-compatible surface and is absent from the OpenAI-compatible supported-field list. [Ollama docs: Tool calling](https://docs.ollama.com/capabilities/tool-calling); [Ollama docs: OpenAI compatibility](https://docs.ollama.com/api/openai-compatibility)
- **llama.cpp structured output**: server flags `-j/--json-schema` and `-jf/--json-schema-file` constrain generations to a JSON schema; raw grammars via `--grammar`/`--grammar-file`; per-request `json_schema`; and `/v1/chat/completions` `response_format` supports both `json_object` and `json_schema`. [llama.cpp server README](https://github.com/ggml-org/llama.cpp/blob/master/tools/server/README.md) (master, fetched 2026-10-15)
- Schooling from the nightly notes: b10947 (Sep 2026) "Refactored JSON schema handling to use common internal representation; updated json-schema-to-grammar" — the schema→grammar path is maintained, not frozen. [R] (Aggregator summary of build notes; verify commit before relying on it.) [Freedom.Tech llama.cpp release history](https://freedom.tech/project/llama-cpp/)

### Inferences
- For KENN's typed planner, the safest 2026 stack is: Ollama 0.40.x `format` schema + `enable_thinking=false` + temperature 0, with the KENN schema embedded in the system prompt. llama.cpp's `--json-schema` is the equivalent when KENN needs slot-level control (per-slot context, grammar pinning).
- `tool_choice` not being supported in Ollama's OpenAI-compatible surface matters if KENN ever wants to force "no tools" on a small model turn; the native `/api/chat` `tools` field can just be omitted instead.
- Do not build on MLX directly for planner JSON unless Outlines is acceptable as a dependency; otherwise keep the planner on the llama.cpp/Ollama path and reserve MLX for speed experiments.

## Key Question 3 — Latency techniques on Apple silicon (spec decoding, KV quant, prompt caching, context trimming)

### Takeaway
The biggest latency-relevant change since KENN's last measurement is that Ollama 0.40.x runs supported models on an **MLX runner by default on Apple Silicon**, and that runner contains its own persistent speculative-decoding subsystem (present by v0.32.6, reliability fixed in 0.40.4). KV-cache quantization (q8_0/q4_0) and prompt caching remain available on the llama.cpp path, and mlx-lm exposes both speculative decoding (`--draft-model`, CLI default 3 draft tokens) and KV quantization (`kv_bits`). The 16 GB constraint argues for q8_0 KV + explicit context caps (Ollama's default for <24 GiB "VRAM" is only 4k tokens), not for larger contexts. **Staleness note: every KENN latency number was measured on Ollama 0.34.4 with the llama.cpp runner; none of it may be quoted as current until it is re-measured on 0.40.x.**

### Cited Findings
- **Ollama context default**: docs state Ollama defaults to **4k context below 24 GiB VRAM**, 32k at 24–48 GiB, 256k above. Set `OLLAMA_CONTEXT_LENGTH` or `num_ctx`; agent-style workloads are advised to use ≥64k. KENN's prior measured runner was 4096. [Ollama docs: Context length](https://docs.ollama.com/context-length)
- **Ollama KV-cache quant**: `OLLAMA_KV_CACHE_TYPE` (global, applies to all models) with `f16` default, `q8_0` ≈ half the memory with "very small" quality loss, `q4_0` ≈ quarter with "small-medium" loss; requires Flash Attention, which Ollama enables automatically when supported (`OLLAMA_FLASH_ATTENTION=1` forces). Docs warn high-GQA models (Qwen2 cited) can lose more precision — relevant to Qwen3.5-4B's 16Q/4KV heads. [Ollama docs: FAQ — Flash Attention and KV cache](https://docs.ollama.com/faq)
- **Ollama MLX runner**: v0.40.0 (2026-09-25) — "on Apple Silicon devices, model architectures supported by the MLX runtime will automatically run on MLX", explicitly including `gemma4`, `qwen3.6`, `qwen3.5` and decision models. [Ollama v0.40.0 notes](https://github.com/ollama/ollama/releases/tag/v0.40.0)
- **Ollama speculative decoding state**: (a) the llama.cpp path only enables spec decode when an embedded/external draft exists — the repo test is literally named "no draft model leaves speculative decoding disabled" and `externalDraftType` maps draft weights to `dflash` or `MTP`. (b) The **MLX runner has a dedicated subsystem** (`mlxrunner/speculate.go`: "persistent speculative-decoding subsystem of a Runner — one per loaded model", with draft sessions that "learn the conversation through the committed-stream reports"). This subsystem is not new: **v0.32.6 (2026-08-04)** — "Qwen3.5 is faster on Apple GPUs: the MLX engine now uses the model's MTP head for speculative decoding automatically" — and **v0.34.2 (2026-09-15)** fixed "excessive memory growth during long generations with MLX speculative decoding". What v0.40.0 changed is routing (supported models reach MLX by default), and v0.40.4 (2026-10-12) "Improved speculative decoding reliability in the MLX runner, including recurrent state handling after rollback". So speculation has been reachable longer than the 0.40 line implies — but only when the request runs on the MLX runner; a llama.cpp-runner request still needs a draft model. [V] [mlxrunner/speculate.go](https://github.com/ollama/ollama/blob/main/mlxrunner/speculate.go); [v0.32.6 notes](https://github.com/ollama/ollama/releases/tag/v0.32.6); [v0.34.2 notes](https://github.com/ollama/ollama/releases/tag/v0.34.2); [v0.40.4 notes](https://github.com/ollama/ollama/releases/tag/v0.40.4)
- **Ollama reuse/caching**: v0.40.4 "improved inference performance by reusing verified manifests and already loaded models"; v0.40.3 paused the *background model upgrade* path "for embedding and other request performance" — i.e. resident-model reuse is now the performance-sensitive surface. [v0.40.4](https://github.com/ollama/ollama/releases/tag/v0.40.4); [v0.40.3](https://github.com/ollama/ollama/releases/tag/v0.40.3)
- **llama.cpp latency surface** (server README, master 2026-10-15): `--cache-prompt` default **enabled**; `--cache-reuse N` KV-shifting reuse (default 0); `--slot-save-path` for slot KV persistence; per-slot context (`--kv-unified-per-slot N`); `-ctk/-ctv` per-K and per-V cache types (f32…q4_0); speculative decoding with `--spec-draft-n-max` default **3** plus a full draft-model flag family (`--spec-draft-hf`, cache types for draft, thread pinning); context checkpoints `--ctx-checkpoints` default 32. ## Key Question 6 — STT for push-to-talk

### Takeaway
**whisper.cpp remains the zero-dependency MIT default for PTT on this machine** (Apple Silicon is a first-class target; 273 MB of memory for tiny through 3.9 GB for large, Metal GPU by default). Three credible accuracy-per-byte challengers appeared or matured in 2026: **Parakeet TDT 0.6B v3** (NVIDIA weights CC-BY-4.0, 25 European languages, Apache-2.0 MLX port by senstella), **Moonshine** (MIT code *and* models by default, built streaming-first, tiny 1 MB micro models, publisher claims better accuracy than Whisper Large V3) and **VibeVoice-ASR-Streaming** (MIT, 1.5B/7B, speaker-aware streaming). **Voxtral Mini 4B Realtime** (Apache-2.0) is the strongest streaming option if a 4B model fits alongside Live, but at 4B it competes with the chat model for RAM. For B4's stated scope ("local whisper.cpp push-to-talk … one at a time", [KENN_PLAN.md line 2374](../../../KENN_PLAN.md)), whisper.cpp is the pinned baseline; Parakeet/Moonshine are the next trial, not the first.

### Cited Findings
- **whisper.cpp** (ggml-org/whisper.cpp, MIT, repo pushed 2026-10-12): "Apple Silicon first-class citizen — optimized via ARM NEON, Accelerate framework, Metal and Core ML"; on Apple Silicon "inference runs fully on the GPU via Metal"; integer quantization (e.g. `q5_0`) is built in; VAD support; XCFramework for Apple platforms; C-style API in `whisper.h`. The bundled `stream` example "samples the audio every half a second and runs the transcription continuously" (`--step 500`). [whisper.cpp README](https://github.com/ggml-org/whisper.cpp) (fetched 2026-10-15)

## Key Question 7 — TTS for spoken feedback

## Key Question 8 — Wake word

### Takeaway
**openWakeWord's licence splits in a way that matters — Apache-2.0 code, CC-BY-NC-SA-4.0 shipped pretrained models — but the adjacent lineage now has a fully clean alternative: microWakeWord's model collection (`esphome/micro-wake-word-models`) is Apache-2.0 including the trained `.tflite` weights.** For a closed-source product there are two clean routes: ship microWakeWord models as-is, or use the Apache-2.0 openWakeWord training pipeline to train KENN's own wake-word model from synthetic speech (<1 hour in the provided Colab notebook). Porcupine's repo is Apache-2.0 but the runtime needs a Picovoice AccessKey and has per-language commercial terms — it is a hosted dependency, not local-first, and it needs a terms review before it can be considered at all. Note that B4's committed scope is push-to-talk, which sidesteps the wake-word problem entirely; this section is groundwork for a later "always listening" decision, not a current requirement.

### Cited Findings
- **openWakeWord** (`dscripka/openWakeWord`, Apache-2.0, pushed 2025-12-30, 2.8k stars): architecture is 80 ms frames through a shared frozen feature extractor (a re-implementation of Google's TFHub speech-embedding model, itself Apache-2.0) plus per-phrase classifiers; "a single core of a Raspberry Pi 3 can run 15-20 openWakeWord models simultaneously in real-time"; ONNX and TFLite runtimes; ONNX-first on Windows. [openWakeWord README](https://github.com/dscripka/openWakeWord) (fetched 2026-10-15)
- **The licence split (the load-bearing line)**: "All of the code in this repository is licensed under the **Apache 2.0** license. All of the included pre-trained models are licensed under the **Creative Commons Attribution-NonCommercial-ShareAlike 4.0 International** license due to the inclusion of datasets with unknown or restrictive licensing as part of the training data. If you are interested in pre-trained models with more permissive licensing, please raise an issue and we will try to add them to a future release." [openWakeWord README §License](https://github.com/dscripka/openWakeWord)
- **Training pipeline is the clean path**: models are trained on "100% synthetic" speech (TTS-generated clips for the wake phrase, minimum several thousand, plus ~30,000 hours of negative data for the released models); the Colab notebook "allows anyone to produce a custom model very quickly (<1 hour) and doesn't require any development experience", with a more detailed notebook for production quality. English only today ("primarily because the pre-trained text-to-speech models used to generate training data are all based on english datasets"). Custom verifier models can second-stage-filter for known voices. A C++ port exists (`rhasspy/openWakeWord-cpp`) if KENN wants it outside Python. [openWakeWord README §Training / §Models](https://github.com/dscripka/openWakeWord)
- **microWakeWord** (`kahrendt/microWakeWord`, Apache-2.0, pushed 2026-07-09; now an Open Home Foundation library): the low-power lineage openWakeWord itself recommends for microcontrollers. Detection is two-stage — 40 spectrogram features every 10 ms at 16 kHz, then a streaming MixConv classifier; training data comes from the Piper sample generator, the same synthetic-data approach as openWakeWord. **Its shipped models are Apache-2.0 including the weights**: `esphome/micro-wake-word-models` (pushed 2026-10-01) states "These terms cover the entire contents of this repository, including the trained model weights (`.tflite`) and their manifests (`.json`). There are no separate or additional terms for the model binaries." That makes it the only fully licence-clean pretrained wake-word package found in this lane. [V] [kahrendt/microWakeWord](https://github.com/kahrendt/microWakeWord); [esphome/micro-wake-word-models](https://github.com/esphome/micro-wake-word-models)
- **Picovoice Porcupine** (`Picovoice/porcupine`, repo Apache-2.0, pushed 2026-10-07, 4.9k stars): README states the runtime requires a free **AccessKey** ("Sign up or Login to get your AccessKey"), and on additional languages: "commercial customers case-by-case" (README line 96 in the fetched copy). The Apache-2.0 repo licence covers the bindings, not the licensed detection engines. → **Terms review required; not a drop-in local dependency.** [Picovoice/porcupine](https://github.com/Picovoice/porcupine)

### Inferences
- If KENN ever ships an always-listening wake word, the Apache-2.0-clean configuration is: openWakeWord **code** for feature extraction + classification, with a **KENN-trained model** produced by the synthetic-data pipeline, checked into the repo as a first-party asset. That keeps code and model licences unambiguous and costs <1 hour of training per phrase plus data-generation time. **Inference from the README's own guidance.**
- A wake word adds a continuously-running audio path (mic privacy indicator, always-on ML privacy story). PTT avoids both the licence and the privacy surface; the B4 plan already chose PTT. Keep wake word out of scope until a product requirement forces it. **Inference.**
- If a wake word is later required, microWakeWord is now the clean default (Apache-2.0 code + Apache-2.0 shipped models), with a KENN-trained openWakeWord model as the route for custom phrases. **Inference.**
